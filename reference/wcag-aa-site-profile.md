# WCAG 2.2 Level A/AA site profile — Midway Music & Arts Fest

**Audience: Claude agents running an accessibility audit of this repo.** Read
this instead of `reference/Web Content Accessibility Guidelines (WCAG) 2.2.html`
(512 KB). Every Level A and Level AA success criterion in WCAG 2.2 is
enumerated below with a disposition. Nothing here quotes the spec; it states
what "pass" means *for this site* and how to check it.

Criterion numbers, titles and levels were extracted mechanically from the spec
copy in `reference/`, not from memory: **31 Level A + 24 Level AA = 55**.
(4.1.1 Parsing is listed in the spec as "Obsolete and removed" and carries no
level; it is not audited — see the a11yproject gaps section.)

**This document does not record audit results.** Findings go in
`reviews/2026-08-wcag-aa-audit.md`. If a disposition here turns out to be
wrong, fix it here first, then audit against the corrected version.

---

## Site facts that drive the dispositions

N/A calls below cite these by tag. Each was verified by inspection on
2026-08-10, not inferred from the site's description. **If one of these facts
stops being true, every criterion citing it must be re-audited** (see re-audit
triggers at the end).

- **S1 — No time-based media.** No `<audio>`, `<video>`, `<track>`, `<object>`,
  `<iframe>` or embedded player anywhere under `site/`. Content is
  CSV-derived text, inline SVG, and sponsor logo images.
- **S2 — No form controls.** Zero `<form>`, `<input>`, `<select>`,
  `<textarea>`, `<label>` elements in `site/index.html` or `site/js/`. Every
  interaction is an `<a>`, a `<button>`, or a map-SVG `<g role="button">`.
- **S3 — No authentication, transactions, or user-submitted data.** All client
  state is two `localStorage` keys (`mfc:starred`, `mfc:dismissed-banner`) set
  by button taps. No server runtime, so no sessions and no timeouts.
- **S4 — One HTML document, hash-routed.** `site/index.html` plus routes
  `#/now #/schedule #/map #/event/<id> #/starred #/vendors #/sponsors`, which
  swap the contents of `<main id="view">`. `document.title` is set once at boot
  from `settings.festival_name` and never per route.
- **S5 — Zero external resources.** System font stack; no CDN, analytics, ads,
  fonts, or third-party widgets. Every byte is self-hosted.
- **S6 — The map is inline SVG and fully inspectable.** `site/assets/map.svg`
  (1.87 MB, generated by `tools/make-map.mjs` — note: *`tools/`*, not
  `scripts/`) declares every color, font size and stroke width in a single
  `<style>` block. `site/js/views/map.js` clones it into the DOM and overlays
  pins at runtime. No raster imagery. The audit's step-0 inspectability
  assumption holds.
- **S7 — Map symbols and labels hold a constant on-screen size.** 467
  `.map-label__scale` groups and every `.pin__scale` group are counter-scaled
  by `view.w / 3000` on each zoom, so zooming the map never enlarges its type.
  Rendered size therefore depends only on the frame width (`.map-frame`
  `max-width: 560px`, square, `#view` padding 1 rem each side).
- **S8 — Only two animations.** The infinite `you-are-here` pulse (2 s
  `@keyframes`) and the toast fade/slide. Both are disabled under
  `prefers-reduced-motion: reduce`. Nothing flashes; nothing autoplays.
- **S9 — One auto-updating view.** `site/js/views/now.js` runs
  `setInterval(draw, 60_000)`; `paint()` is a no-op when the computed key is
  unchanged, but on a change it replaces `#view.innerHTML` wholesale.
  `site/js/views/starred.js` removes an un-starred row after
  `UNDO_GRACE_MS = 3000`.
- **S10 — No hover-revealed content and no `title` attributes.** The CSS
  contains no `:hover` rule at all, and no element carries a `title` tooltip.
- **S11 — Text content is organizer-supplied at build time.** Venue, event,
  vendor and sponsor text comes from the Google Sheet. Sponsor logo alt text
  is *derived* (`alt="<name> logo"` in `site/js/views/sponsors.js`), not
  authored by the organizers — there is no alt-text column.

## Check-method tags

- **`code`** — read the source; no runtime needed.
- **`axe`** — an `@axe-core/playwright` rule covers it (already a
  devDependency; `package.json` is the orchestrator's file).
- **`pw`** — a Playwright assertion drives the DOM/keyboard/viewport.
- **`calc`** — programmatic computation over `site/assets/map.svg` or
  `site/css/app.css` (contrast ratios, rendered sizes). Never eyeball these.
- **`human`** — cannot be settled without a real device or assistive
  technology. These stay **pending** in the report until Anthony runs the
  device checklist.

## 1. Perceivable

**1.1.1 Non-text Content** · A · **applicable**
Pass: every `<img>` has an `alt`; purely decorative inline SVG carries
`aria-hidden="true" focusable="false"` (tab-bar icons, legend swatches, venue-key
diamonds); informative glyphs carry `role="img"` + `aria-label` (ticket icons,
age badges, the share glyph); the map SVG has a non-empty accessible name and a
text alternative for the information it conveys.
Check: `axe` `image-alt`, `svg-img-alt`, `role-img-alt`, `aria-hidden-focus` on all
7 routes; `code` for any new inline SVG; `human` judgment on whether the venue
key list + venue/transit sheets constitute an adequate alternative for a
complex image (a11yproject calls maps out explicitly). Note S11: sponsor logo
alt is derived from the name, so a logo whose meaning exceeds its name has no
way to say so — that is a content-pipeline finding, not a code fix.

**1.2.1 Audio-only and Video-only (Prerecorded)** · A · **n/a** — S1.
**1.2.2 Captions (Prerecorded)** · A · **n/a** — S1.
**1.2.3 Audio Description or Media Alternative (Prerecorded)** · A · **n/a** — S1.
**1.2.4 Captions (Live)** · AA · **n/a** — S1; the site has no live stream and
DEFINITION.md excludes a server runtime that could carry one.
**1.2.5 Audio Description (Prerecorded)** · AA · **n/a** — S1.

**1.3.1 Info and Relationships** · A · **applicable**
Pass: structure is in the markup, not just the styling — real `<h1>`–`<h3>` in
sequence with exactly one `<h1>` per route; `<ul>`/`<ol>`/`<li>` for every list;
landmarks `<header>` / `<main id="view">` / `<nav aria-label="Primary">`; star
state exposed via `aria-pressed`, not a `★`/`☆` glyph alone; the schedule's day
and group-by switchers are `role="group"` + `aria-pressed` (CONTRACTS.md bans
`role="tablist"` — do not "fix" that to a tabs pattern).
Check: `axe` `heading-order`, `page-has-heading-one`, `list`, `listitem`,
`landmark-one-main`, `landmark-unique`, `aria-allowed-attr` per route; `code`
for new markup.

**1.3.2 Meaningful Sequence** · A · **applicable**
Pass: DOM order matches reading order. The event row's text column and label
column are siblings in visual order (CONTRACTS.md: labels beside the text, not
above it). No CSS `order`, `row-reverse` or `column-reverse` currently
reorders content — verify none was added.
Check: `code` grep `site/css/app.css` for `order:` / `*-reverse`; `pw` assert
event-row child order.

**1.3.3 Sensory Characteristics** · A · **applicable**
Pass: no instruction depends on shape, size, position, or sound. Current copy
satisfies this by naming keys and controls ("Use the arrow keys to pan, and the
zoom buttons below…") and by labelling every legend swatch in text.
Check: `code` review of every user-facing string in `site/js/` and
`site/index.html` for "above/below/right/the round button".

**1.3.4 Orientation** · AA · **applicable**
Pass: content is not restricted to a single display orientation.
**`site/manifest.webmanifest` currently declares `"orientation": "portrait"`,
which is exactly the restriction this criterion prohibits** unless portrait is
essential (it is not — this is a map and a list). The browser tab is
unaffected; an installed standalone PWA is the exposure.
Check: `code` the manifest; `human` rotate an installed instance on a real
iPhone and confirm whether it follows the device.

**1.3.5 Identify Input Purpose** · AA · **n/a** — S2; no field collects
information about the user, so there is nothing to mark with an
`autocomplete` token.

**1.4.1 Use of Color** · A · **applicable**
Pass: color is never the only visual means of conveying information. Current
design mostly satisfies this by construction — kind badges carry the kind
word; ticket and age glyphs carry labels; venue pins carry a number and
transit pins a line letter; featured vs. generic sponsor pins differ by
fill vs. outline. **The unresolved case is the map's two rail lines**, drawn
only as `#2f7d4f` (Green) and `#2b5fa8` (Blue) with identical weight, no
labels, and no legend entry.
Check: `code` inventory of every meaning-bearing color; `pw` screenshot each
route under a grayscale filter and confirm nothing becomes ambiguous.

**1.4.2 Audio Control** · A · **n/a** — S1; nothing plays automatically or at all.

**1.4.3 Contrast (Minimum)** · AA · **applicable**
Pass: text ≥ 4.5:1 against its actual background; ≥ 3:1 for large text (≥ 24 px,
or ≥ 18.66 px bold). Applies to the app shell, the six kind-badge tints, *and*
every `<text>` element inside the map SVG.
Check: `axe` `color-contrast` for HTML; `calc` for SVG text — parse the
`<style>` block of `site/assets/map.svg` and compute against the paper fill
`#eeeeec` and every fill a label can sit over. Baseline computed 2026-08-10:
spine label `#3f3f3f` 9.06:1, arterial `#565654` 6.33:1, station `#3d5c4d`
6.37:1 — all pass; **the SVG's own `.attribution` text `#8c8c8a` is 2.90:1 and
fails** (it sits at the extreme bottom edge of the full extent, so it is
off-screen at the home view — decide whether it is visible text or dead
markup).

**1.4.4 Resize Text** · AA · **applicable**
Pass: at 200% no content or functionality is lost. The viewport meta sets no
`user-scalable=no` or `maximum-scale`, so pinch-zoom is available.
Check: `pw` each route at 200% page zoom, assert no clipping and no horizontal
scroll; `human` for the map, where the nuance lives — per S7, map labels are
sized in SVG user units and counter-scaled, so **zooming the map never makes
its type larger**, and desktop text-only zoom does not touch SVG at all. Page
zoom does scale the whole frame, which is the argument for a pass.

**1.4.5 Images of Text** · AA · **applicable**
Pass: no text is presented as an image except logotypes. The brand logo and
sponsor logos are the logotype exception. The generated ticket sprite in
`index.html` contains `<path>` outlines spelling "FREE" — confirm it reads as
an icon/logotype rather than body text, given it also carries an `aria-label`.
Check: `code` the sprite and any new inline SVG; `code` inventory of
`site/assets/sponsors/` — a sheet-supplied logo containing a tagline in text is
a content-pipeline rule, not something the build can currently catch.

**1.4.10 Reflow** · AA · **applicable**
Pass: at 320 CSS px wide there is no two-dimensional scrolling, and the six-tab
bar still fits and reads (CONTRACTS.md states this explicitly). The map itself
is within the SC's stated exception for content requiring two-dimensional
layout; the legend, attribution, and venue key list below it are not.
Check: `pw` viewport 320 × 256 per route, assert
`scrollWidth <= clientWidth` on the scrolling element and that no tab label is
clipped.

**1.4.11 Non-text Contrast** · AA · **applicable**
Pass: ≥ 3:1 for (a) UI component boundaries and states and (b) graphical
objects required to understand the content. Covers the focus outline
(`#0b3f5a`), button borders, the star glyph, map pins against the paper,
legend swatches against the card, and — the judgment call — whether the base
map's streets and water count as "required to understand".
Check: `calc` over the SVG `<style>` block and the CSS custom properties.
Baseline computed 2026-08-10 against paper `#eeeeec`: venue pin `#10577b`
6.77:1, sponsor `#a11f22` 6.61:1, transit `#298d4e` 3.61:1, Green Line
`#2f7d4f` 4.34:1, Blue Line `#2b5fa8` 5.47:1 — all pass. **Street fills are
1.16–1.35:1 and the water fill 1.35:1** — a fail if streets are held to be
required for understanding a wayfinding map, a pass if they are decorative
ground under the labels. `axe` covers almost none of this; do not rely on it.

**1.4.12 Text Spacing** · AA · **applicable**
Pass: with line-height 1.5×, paragraph spacing 2×, letter-spacing 0.12em and
word-spacing 0.16em applied, no content is lost or clipped. The badge
(`white-space: nowrap`) and the six-tab bar are the likely pressure points.
Check: `pw` inject the four overrides as a stylesheet, then assert no element
overflows its parent, per route at 320 px.

**1.4.13 Content on Hover or Focus** · AA · **n/a** — S10: the CSS contains no
`:hover` rule and no element has a `title` attribute, so no additional content
appears on hover or focus. Sheets and toasts are click-triggered. Becomes
applicable the moment a tooltip, popover, or hover-revealed control is added.

## 2. Operable

**2.1.1 Keyboard** · A · **applicable**
Pass: every function is keyboard-operable — nav links, star buttons, day and
group-by toggles, sheet open/close, map pan (arrow keys on the focused SVG,
which is `tabindex="0" role="group"`), pin traversal (roving `tabindex`, arrow
keys between pins in view) and pin activation (Enter/Space), the zoom/reset/
locate buttons, and the venue key list.
Check: `pw` keyboard-only walkthrough of every route —
`tests/a11y.spec.mjs` already covers map panning and sheet focus; extend rather
than duplicate. `axe` cannot detect this.

**2.1.2 No Keyboard Trap** · A · **applicable**
Pass: focus can always leave every component. The sheet is a native `<dialog>`
opened with `showModal()`, so the trap is the browser's and Escape closes it;
on close, focus returns to the trigger.
Check: `pw` tab repeatedly inside the open sheet and confirm it cycles, Escape
closes, and focus lands back on the opener (partly covered already).

**2.1.4 Character Key Shortcuts** · A · **n/a** — no shortcut is bound to a
letter, number, punctuation or symbol key. The only `keydown` handlers are on
the map SVG and its pins (arrow keys, Enter, Space), and both are active only
while that component has focus, which the SC exempts. Becomes applicable if a
document-level key handler is added.

**2.2.1 Timing Adjustable** · A · **applicable**
Pass: no time limit is set on reading or completing an action. Two timers exist
(S9): the Now view's 60 s redraw, which changes content rather than expiring an
action, and the starred view's 3 s undo grace period. **The grace-period claim
to verify: un-starring takes effect immediately on tap and the row's lingering
presence is only an undo affordance — the event can still be re-starred from
any list afterwards — so nothing is lost when the timer fires.** If that holds,
this passes; if the row were the only route back, it would fail.
Check: `code` `site/js/views/starred.js` and `store.js`; `pw` assert an event
can be re-starred after the grace period elapses.

**2.2.2 Pause, Stop, Hide** · A · **applicable — and the least settled entry here**
Two triggers, neither obviously exempt:
(a) the `you-are-here` pulse is moving content that starts automatically, runs
indefinitely, and is presented in parallel with other content. Honoring
`prefers-reduced-motion` is good practice but is **not** the mechanism this SC
asks for (a pause/stop/hide control), so the pass has to rest on the animation
being essential or on the user having initiated it by tapping locate.
(b) the Now view auto-updates every 60 s (auto-updating information), and on a
key change replaces `#view.innerHTML`, which destroys focus and reading
position inside it.
Check: `code` + `human` judgment; record the reasoning explicitly rather than
waving it through.

**2.3.1 Three Flashes or Below Threshold** · A · **applicable (trivially)**
Pass: nothing flashes more than three times per second. The only animations are
a 2 s pulse and a 0.25 s toast transition (S8).
Check: `code` every `@keyframes` and `transition` in `site/css/app.css`.

**2.4.1 Bypass Blocks** · A · **applicable**
Pass: a mechanism exists to skip repeated blocks. The repeated blocks are the
`<header>` (logo + visually-hidden festival name) and the tab bar — and the tab
bar sits **after** `<main>` in DOM order, so almost nothing precedes the main
content. ARIA landmarks are the accepted mechanism here. There is no skip link.
Check: `code` landmark structure; `axe` `bypass`, `region`. Note that
a11yproject asks for a visible-on-focus skip link regardless of landmarks —
see the gaps section.

**2.4.2 Page Titled** · A · **applicable**
Pass: the page has a title describing its topic. Per S4 there is exactly one
title for all seven routes, set from `settings.festival_name`. The SC is
written for documents, and this is one document; the counter-argument is that
each route has its own URI and behaves as a page. The `#route-announcer` live
region partly compensates.
Check: `pw` assert a non-empty title on load; the per-route question is a
judgment the audit must decide and record, not assume.

**2.4.3 Focus Order** · A · **applicable**
Pass: focus order preserves meaning and operability. Specifics that matter:
route change moves focus to `#view`; the sheet takes focus on open and returns
it on close; the whole pin set is one tab stop via roving `tabindex`, and pins
panned off screen drop out of the tab order.
Check: `pw` record the focus sequence per route and compare to visual order;
existing coverage in `tests/a11y.spec.mjs`.

**2.4.4 Link Purpose (In Context)** · A · **applicable**
Pass: each link's purpose is clear from its text plus programmatically
determined context. Event row links carry time + title + venue. The repeated
"Open in Google Maps" links sit inside a `<dialog>` labelled by the venue,
sponsor or stop name, which supplies the context.
Check: `axe` `link-name`; `code` for any link whose text repeats without a
labelled ancestor.

**2.4.5 Multiple Ways** · AA · **applicable, with a scope caveat**
Pass: more than one way to locate each route. Available: the six-tab bar, plus
in-content paths (event rows → event detail, map pins and the venue key list →
venue sheet, sheet event lists → event detail, schedule regrouping). Search is
an explicit DEFINITION.md non-goal and is not needed to satisfy this.
Caveat worth recording once: the SC governs "a set of Web pages", and this is
literally one page (S4); reading the hash routes as pages is the conservative
interpretation, and it passes under that reading.
Check: `code`.

**2.4.6 Headings and Labels** · AA · **applicable**
Pass: headings and labels describe topic or purpose. Two `sr-only` headings
exist by design — the Map view's `<h1>Map</h1>` and the legend's `<h2>Legend</h2>`
— and both still need to be descriptive since they are the accessible names
screen-reader users navigate by. Glyph-only buttons carry `aria-label`
("Zoom in", "Zoom out", "Reset view", "Show my location", "Dismiss notice",
"Close", "Star <title>").
Check: `axe` `empty-heading`, `button-name`, `link-name`; `code` for
descriptiveness, which axe cannot judge.

**2.4.7 Focus Visible** · AA · **applicable**
Pass: every keyboard-focusable element shows a visible focus indicator.
Current: `a:focus-visible, button:focus-visible { outline: 3px solid #0b3f5a;
outline-offset: 2px }` and `.circuit-map-svg:focus-visible, .pin:focus-visible`
with `outline-offset: -3px` (negative because `.map-frame` has
`overflow: hidden` and would clip an outside outline).
Check: `pw` focus each focusable element and assert a non-`none` computed
outline; confirm the pin outline is not clipped at the frame edge. `#view`
(`tabindex="-1"`) is focused programmatically and needs no indicator.

**2.4.11 Focus Not Obscured (Minimum)** · AA · **applicable**
Pass: when an element receives focus it is not *entirely* hidden by
author-created content. Exposure: `.tab-bar` is `position: fixed; bottom: 0`
(60 px + safe area), the schedule's control bars are `position: sticky; top`,
and `#toast-root` is fixed above the tab bar.
Check: `pw` focus every focusable element in turn and assert
`document.elementFromPoint()` at its center returns the element or a descendant.

**2.5.1 Pointer Gestures** · A · **applicable**
Pass: multipoint and path-based gestures have a single-pointer, non-path
alternative. Pinch-zoom (multipoint) is covered by the `+` / `−` / reset
buttons and by double-tap-to-zoom. Drag-panning is very likely **not**
path-based — only the net displacement is used, never the route the finger
took — which puts panning under 2.5.7 instead. Record that reasoning rather
than repeating the analysis in both entries.
Check: `code` `setupInteraction()` in `site/js/views/map.js`.

**2.5.2 Pointer Cancellation** · A · **applicable**
Pass: no function completes on the down-event, and an accidental press can be
aborted. Map taps are dispatched on `pointerup` behind a 10 px move threshold
and a 600 ms timeout; every other control uses `click`.
Check: `code`; `pw` press, move beyond the threshold, release, and assert no
sheet opened.

**2.5.3 Label in Name** · A · **applicable**
Pass: where a control presents visible text, its accessible name contains that
text. Venue key buttons pass by construction (the visible venue name *is* the
name). The cases to judge: the zoom buttons show `+`, `−`, `⟲` while their
accessible names are "Zoom in", "Zoom out", "Reset view", and the banner
dismiss shows `×` against "Dismiss notice" — glyphs are arguably not visible
text labels, but the call should be recorded.
Check: `code` every `aria-label` that sits next to visible glyph or text.

**2.5.4 Motion Actuation** · A · **n/a** — no function is operated by device
motion or user motion. The only sensor use is `navigator.geolocation`, invoked
solely by an explicit tap on the locate button (never on load), which the SC
does not cover.

**2.5.7 Dragging Movements** · AA · **applicable — likely the sharpest map finding**
Pass: any function operated by dragging has a single-pointer alternative that
does not require dragging, unless dragging is essential. Map **panning** is
drag-operated. The zoom, reset and double-tap controls change scale, not
position, and arrow-key panning is keyboard, which this SC does not accept as
the alternative. So today there is **no single-pointer non-drag way to pan**.
Whether panning a map is "essential" is the judgment the audit must make and
justify; note that a mapping library would not automatically resolve it.
Check: `code` `setupInteraction()`.

**2.5.8 Target Size (Minimum)** · AA · **applicable**
Pass: targets are ≥ 24 × 24 CSS px, or spaced so that a 24 px-diameter circle
centered on each does not intersect another target's circle. App-shell controls
are built to a 44 px minimum. Map pins are the exposure, because their rendered
size tracks the frame width (S7). Computed 2026-08-10 at the home view — hit
diamond bounding boxes:

| frame width | venue hit | transit / sponsor hit |
|---|---|---|
| 288 px (320 px viewport) | 27.8 px | **22.7 px** |
| 358 px (390 px viewport) | 34.6 px | 28.2 px |
| 560 px (the cap) | 54.1 px | 44.1 px |

Only the narrowest phone falls short, and only for non-venue pins; the spacing
exception probably rescues it wherever pins are not clustered, which is the
thing to check rather than assume.
Check: `calc` + `pw` measure `getBoundingClientRect()` on every
`.pin__hit` and every control at 320 px and 560 px, then evaluate the spacing
exception against actual pin positions.

## 3. Understandable

**3.1.1 Language of Page** · A · **applicable**
Pass: `<html lang="en">` — present.
Check: `axe` `html-has-lang`, `html-lang-valid`.

**3.1.2 Language of Parts** · AA · **applicable, content-dependent**
Pass: any passage in a language other than English carries a `lang` attribute.
Site chrome is entirely English. Sheet-supplied venue, event, vendor and
sponsor text (S11) could contain a non-English phrase; proper names are exempt,
which covers most realistic cases.
Check: `code` review of `content.json` at content freeze. There is no build
validation for this and adding one is probably not worth it — say so rather
than inventing a rule.

**3.2.1 On Focus** · A · **applicable (trivially)**
Pass: receiving focus does not change context. The only programmatic focus
moves are the app's own (`#view` on route change, the dialog on open, the
trigger on close), and none is triggered *by* a user focusing something.
Check: `code` grep for `focus` handlers.

**3.2.2 On Input** · A · **n/a** — S2: there are no input fields or setting
controls whose *setting* a user changes; every state change comes from
activating a `<button>`, which the SC treats as activation, not input.
**The borderline to re-check** if this is ever revisited: the day and group-by
toggles and the star buttons carry `aria-pressed` and do change the view's
content on activation. That is expected activation behavior, not an automatic
context change on input — but it is the nearest thing on the site.

**3.2.3 Consistent Navigation** · AA · **applicable**
Pass: repeated navigation keeps the same relative order across routes. This is
structurally guaranteed — `.tab-bar` is a single element in `index.html` that
routes never re-render; only `aria-current`/`is-active` change.
Check: `code`; `pw` assert nav link order is identical on every route.

**3.2.4 Consistent Identification** · AA · **applicable**
Pass: components with the same function are identified consistently. The
shared helpers make this mostly structural: `event-row.js` renders every star
button, `sheet.js` renders every "Open in Google Maps" link. The pairs to
verify are the star button in a row vs. in event detail, and the kind badge /
ticket icon meaning the same thing in list and detail views.
Check: `code` across `site/js/views/`.

**3.2.6 Consistent Help** · A · **n/a** — the site offers no help mechanism
(no contact details, help page, FAQ, chat, or human contact option) on any
route, so there is nothing that must appear in a consistent order. The
install-instructions sheet is a one-off affordance, not a help mechanism.
Becomes applicable the moment a "Contact organizers" or FAQ link is added.

**3.3.1 Error Identification** · A · **n/a** — S2/S3: nothing is submitted or
validated. Build-time CSV validation errors are printed to an operator's
terminal, never rendered to an attendee.
**3.3.2 Labels or Instructions** · A · **n/a** — S2: no input fields.
**3.3.3 Error Suggestion** · AA · **n/a** — S2/S3.
**3.3.4 Error Prevention (Legal, Financial, Data)** · AA · **n/a** — S3: no
legal commitment, financial transaction, or user-modifiable data is created by
the site. The donate link navigates off-site; the destination's conformance is
out of scope per DEFINITION.md.
**3.3.7 Redundant Entry** · A · **n/a** — S2/S3: no multi-step process and
nothing is entered at all, let alone twice.
**3.3.8 Accessible Authentication (Minimum)** · AA · **n/a** — S3: no
authentication of any kind, and accounts are an explicit non-goal.

## 4. Robust

**4.1.1 Parsing** — listed in WCAG 2.2 as *Obsolete and removed*; carries no
conformance level and is **not audited**. Malformed markup is still caught
indirectly by 1.3.1 and 4.1.2. a11yproject still asks for valid HTML — see
below.

**4.1.2 Name, Role, Value** · A · **applicable**
Pass: every custom control exposes a correct name, role and state. The
inventory: map pins (`role="button"` + `aria-label` + Enter/Space + roving
`tabindex`), the map SVG (`role="group"` + `aria-label`), star buttons
(`aria-pressed`, kept in sync by `applyStarState`), day and group-by toggles
(`role="group"` + `aria-pressed`), and the sheet (native `<dialog>` with
`aria-labelledby="sheet-title"`, focused itself rather than its close button).
Check: `axe` `button-name`, `link-name`, `aria-valid-attr-value`,
`aria-allowed-attr`, `aria-required-attr` on every route **and with a sheet
open** (a route-only scan never sees the dialog); `code` for new controls.

**4.1.3 Status Messages** · AA · **applicable**
Pass: status messages are programmatically exposed without moving focus. Three
live regions exist: `#route-announcer` (`aria-live="polite" role="status"`,
cleared then reset on the next frame so an unchanged value still announces),
`#toast-root` (`aria-live="polite"`, toasts appended as children — the toast
itself deliberately carries no role, to avoid double announcement), and the
notice banner (`role="status"`).
Check: `pw` assert the announcer's text after each route change, that toast
text lands inside the live region, and that the banner has `role="status"`;
`human` to confirm VoiceOver actually speaks all three, which no automated
check can establish.

## What a11yproject.com/checklist covers that the WCAG AA mapping does not

Cross-checked 2026-08-10. Items below are worth doing but are **not** Level
A/AA success criteria, so they belong in the report as advisory, not as
conformance findings.

- **Validate your HTML.** No longer any SC (4.1.1 removed). Cheap to add as a
  build or CI step if wanted.
- **Provide a skip link, visible on focus.** 2.4.1 is satisfiable by landmarks
  alone, and here the tab bar follows `<main>`, so a skip link buys little —
  but the checklist asks for one unconditionally.
- **Identify links that open in a new tab or window.** The site has 7
  `target="_blank"` links (Google Maps, venue websites, donate) with no
  notice. Only AAA (3.2.5) covers this in WCAG.
- **Remove `title` attribute tooltips** — already satisfied (S10); worth
  keeping as a rule for new code.
- **Avoid `autofocus`** — already satisfied; nothing uses it.
- **Check content in specialized browsing modes** (forced-colors / Windows High
  Contrast). No SC requires it, and it matters more here than usual: an SVG map
  built entirely from declared `fill`/`stroke` values can collapse to
  unreadable under forced colors.
- **Check custom `::selection` colors** — none defined; nothing to check.
- **Ensure sufficient space between interactive items** — overlaps 2.5.8's
  spacing exception; on this site the pressure point is clustered map pins.
- **Remove invisible focusable elements** — already handled deliberately for
  map pins (off-screen pins leave the tab order); re-check if that logic changes.

Checklist items that simply do not apply: everything under Tables (no `<table>`),
Forms (S2), Media / Video / Audio (S1).
