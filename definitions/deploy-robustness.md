# Deploy robustness — publishing through remote-source outages

Status: drafted 2026-08-10, re-verified against the pipeline 2026-08-11;
recommendation pending Anthony's answers to the open questions | Overall
confidence: medium-high — the failure-mode analysis was read out of the
workflows and `build.mjs` rather than assumed, but several load-bearing
GitHub Actions behaviors (toolcache contents, bot-commit loop suppression,
cross-workflow concurrency) are documented-but-untested here and are called
out where they matter.

## Problem & motivation

CLAUDE.md carries an invariant the pipeline does not yet meet: *"The build and
deploy process should be robust against remote sources being unavailable. If
NPM is down, we should still be able to deploy content updates. If a content
spreadsheet is unavailable, we should still be able to deploy a code update
using the latest available data."* Its second and third sentences map
one-to-one onto the two deferred BACKLOG items: a **content-only publish path**
that needs no npm (review finding F21, second half) and a **snapshot fallback**
so a code deploy can ship while the Google Sheet is unreachable, with staleness
marked loudly (F17, second half).

The scenario that gives the invariant its teeth is festival weekend: a code
hotfix has to ship on Saturday morning while Google Sheets is returning 500s,
or a coordinator's schedule fix has to reach phones while the npm registry is
down. Today either outage blocks all deploys. The failure is safe — the last
good deploy stays live — but nothing new can ship.

The first halves of both findings landed in the August review follow-ups:
the content fetch has a 45 s timeout and retries, and CI caches Playwright
browsers keyed on the lockfile. This definition covers the remainder.

## Current failure modes

`deploy.yml` runs two jobs: **test** (`npm ci` → registry; Playwright browsers
→ CDN on cache miss; `install --with-deps` or `install-deps` → apt mirrors on
every run; then the offline suite against fixture content) gating **deploy**
(checkout, then `build.mjs` + `build-sw.mjs` — zero npm dependencies, but
fetching every `https://` content source live, plus any remote sponsor-logo
URLs). `rebuild-content.yml` (6-hour cron + manual) just calls `deploy.yml`, so
every content refresh pays the whole chain.

That the deploy job needs no npm is what makes the content-only path below
possible: the MapLibre engine ships as committed bytes under
`site/assets/maplibre/` rather than being vendored out of `node_modules` at
deploy time, and the map's OSM geometry is likewise a committed artifact
generated by a one-off tool. If a future change generates either at deploy
time instead, the content-only path stops being npm-free and the invariant
breaks again silently.

- **Sheet unreachable at deploy time** (timeouts, 5xx after retries, DNS).
  `build.mjs` exits 1; no deploy. Code pushes and cron rebuilds are equally
  blocked. Nothing broken can be published, but nothing at all can be.
- **Sheet reachable but wrong** — a publish link that has become a sign-in
  page, an emptied tab, a renamed header column. The build fails by design.
  This is the guardrail working, not an outage, and no fallback should fire
  automatically here: those loud failures are how link rot and bad edits get
  noticed.
- **npm registry down.** `npm ci` fails the test job, which blocks the deploy
  job — even though the deploy job itself needs no npm, and even for a pure
  content refresh.
- **Playwright CDN or apt mirrors down.** The browser cache covers the CDN
  when the lockfile is unchanged; the deps install hits apt on every run.
  Residual and rarer; grouped with the npm case below.
- **Both sheet and npm down.** Nothing ships. A content update is not merely
  blocked but pointless — there is nothing fresh to fetch, and the snapshot is
  deliberately not a substitute on that path (see the cron rule below) — while
  a code hotfix is doubly blocked.
- **GitHub Actions or Pages down.** Accepted, out of scope: GitHub is the
  platform, nothing at $0 routes around it, and the offline-first app keeps
  working on phones that have already visited.

One further exposure the review did not flag: sponsor `logo` URLs are fetched
at build time with a timeout but no retries and no fallback. Sponsors are
still a fixture today, but when that tab goes live, a sponsor's flaky logo
host becomes another way a deploy dies. Any design here should cover remote
fetches generically, not the five CSVs specifically.

## Success criteria

- With every `https://` content source unreachable, an operator can still
  deploy a code update built from the latest previously-fetched content, via
  one documented, deliberate action — and the run states loudly, to the
  operator, what is stale and since when.
- With npm (or Playwright's CDN, or apt) unavailable, a content update still
  publishes: the content path invokes no npm at any step.
- Build determinism holds on every path: unchanged sources — live or fallback
  — produce byte-identical `content.json` and an unchanged service-worker
  version.
- The fallback and the content-only path are proven by tests that never touch
  the network, per the existing loopback-fixture convention.
- README gains an operator playbook: what to run when the sheet is down, and
  when npm is down, terse enough to execute at 7am on festival Saturday.

**Failure looks like:** staleness nobody notices (a fallback that fires
silently on cron, pinning rotted content for days), or a normal deploy path
whose tests-first gate got quietly weaker in the name of robustness.

## Non-goals

- **No mitigation for GitHub itself being down**, and no paid mirrors, proxies,
  or secondary hosting of any kind.
- **No always-on test skipping.** The tests-first gate on code deploys stays
  exactly as strict on the normal path.
- **No loosening of content validation.** Wrong-but-reachable sources keep
  failing every build, fallback or not.
- **No app feature work**, beyond the attendee-visible staleness marker *if*
  Anthony wants one (open question 2 — recommended against).
- **No fixture refresh.** The committed fixtures are left alone here. The
  snapshot is machine-written by successful builds and feeds only emergency
  builds; fixtures are hand-committed and feed the offline tests. Their
  overlap on venues is open question 6.

## Constraints

- $0/month; GitHub Pages + Actions only; everything the app needs served from
  the primary origin.
- **Determinism, including its service-worker consequence:** `build-sw.mjs`
  hashes every file under `site/` into the SW version, so a single marker byte
  added to `content.json` forces every phone to re-download the full precache.
  Any staleness marking must respect that.
- Tests stay off the network. Loopback HTTP is the sanctioned way to simulate
  remote sources.
- The coordinator's workflow is untouched: edit the sheet, wait for cron or
  trigger a rebuild. Only venues is live today and the rest are a one-line
  config change away, so every mechanism must be per-source generic.

## Options

**Fallback source — A1: committed snapshot, refreshed by successful live
builds (recommended).** This is not a new idea in this repo so much as an
unfinished one: `tools/make-map.mjs` already fetches OSM geometry through a
primary endpoint, a mirror, and retries, then falls back to a committed
`tools/osm-cache.json`, refetching only under an explicit `--refresh` flag.
The map data survives an Overpass outage for exactly that reason (degrading to
a hardcoded grid only if every source fails); the content pipeline has no
equivalent. `build.mjs` gains a `--write-snapshot` mode: after a successful
load and validation, it writes the bytes of every remotely-fetched resource
(CSV sources and sponsor-logo URLs alike) into `content/snapshot/`, with a
meta file recording each URL, content hash, and the date the bytes last
changed. **Every path that successfully publishes commits the refreshed
snapshot when it differs** (`[skip ci]`; needs `contents: write` on the job,
which is read-only today). That "every path" is a requirement, not redundancy:
the 6-hour cron is how fresh sheet content normally arrives, so a snapshot
refreshed only by `deploy.yml` would be pinned to whenever Anthony last pushed
code — stale by weeks in a quiet stretch, which is precisely the stretch
before a festival-weekend hotfix. The write step is therefore shared by the
deploy job and the content-only job. The fallback itself is an opt-in build
flag (`--use-snapshot`): a remote fetch that fails after retries resolves from
the snapshot instead. Trade-offs: bot commits in history, though only when
sheet content actually changed; a permission widening; and a possible race
with a concurrent push, which is acceptable because the snapshot refresh is
best-effort — missing one cycle is harmless. In exchange, staleness is dated,
fallback inputs go through the same validation as live ones, and byte-fidelity
is trivially testable over loopback. The snapshot adds no new exposure: these
are published-to-web CSV bytes, public already.

**Fallback source — A2: reuse the live deploy's `content.json` (and sponsor
assets) from Pages.** No repo churn and no new permissions, and what you get
is exactly what is currently live. Rejected as primary: it chains one remote
dependency onto another (the fallback dies with Pages, or with the custom
domain); it bypasses build validation at fallback time; `content.json`
deliberately carries no date, so staleness cannot be stated; and the sponsor
logos it references must be crawled out separately. It is the same data as A1,
one hop further away and undated.

**Fallback source — A3: nothing further.** Last-good-stays-live already holds,
and an emergency code deploy is rare. Rejected: the invariant says otherwise,
and the festival-weekend hotfix is precisely the case the project exists to
survive.

**Fallback trigger — opt-in (recommended, provisionally).** A
`workflow_dispatch` input (`use_content_snapshot: true`) passed to the build
flag. A code push while the sheet is down fails loudly, and the operator
re-runs with the flag: the failed run is the alarm, the re-dispatch is the
operator's explicit acknowledgment that stale content is being shipped. The
alternative — automatic fallback on push-triggered deploys only, never on cron
— never blocks a code push, but lets a rotted publish link hide behind every
push while only cron failures still surface it. Anthony's call (open
question 1). Cron rebuilds never fall back under either answer: their only
purpose is fetching fresh content, and "succeeding" on stale content would be
a lie.

**Staleness marking — operator-loud is mandatory; attendee-visible is a
trade.** The mandatory part is free and deterministic, because every message
derives from the snapshot's recorded dates rather than the build clock: a
build-log banner naming each snapshot-sourced file and when its content last
changed, a `::warning::` annotation so the run is visibly flagged in the
Actions UI, and the same line in the job summary. An attendee-visible marker
costs the same whatever the outage: any byte added to `content.json` changes
the SW version, forcing a full re-precache on every phone, twice (marker on,
marker off), for content that is otherwise identical. Its value, by contrast,
scales with outage length. A two-hour Sheets blip leaves content nobody would
call stale; a
multi-day outage is exactly when an attendee would want to know. If wanted,
the cheapest deterministic form is a settings-style field carrying the
snapshot's last-changed date, rendered through the existing notice-banner UI.
Recommended against by default; open question 2.

**Code deploys while npm is down — beyond the invariant, deferred.** The
invariant demands content updates survive npm being down, not code deploys.
Two hardening options exist if Anthony wants more: caching `~/.npm` keyed on
the lockfile with `--prefer-offline` (cheap, removes the registry from
unchanged-lockfile runs, does nothing after a lockfile bump), and an emergency
`skip_tests` dispatch input (fully effective, since the deploy job needs no
npm — but it weakens the deliberately built tests-first gate to one checkbox).
Open question 4.

## Content-only publish path (F21)

Rework `rebuild-content.yml` from "call the whole `deploy.yml` pipeline" into a
self-contained job: checkout → `node scripts/build.mjs && node
scripts/build-sw.mjs` → commit any snapshot change → upload Pages artifact →
deploy, in the same `pages` concurrency group.

No npm anywhere in it. npm-free is not network-free: the job still needs
GitHub for checkout and Pages (accepted above), and `actions/setup-node` still
resolves Node 24 — documented as a toolcache read on the hosted runner,
downloading from nodejs.org only on a miss, unverified here. The registry, the
Playwright CDN and apt leave the path entirely. Dropping `setup-node` for the
runner image's preinstalled Node would close the residual gap but trade a
pinned major for whatever the image ships, which is the worse deal.

This drops the browser suite from content refreshes at no cost: `npm test`
builds from local fixtures, so the suite has never tested live content — on a
content refresh it only re-proves the unchanged code that its own push deploy
already proved. The gate that actually guards content is `build.mjs`
validation, which still runs and still fails loudly.

The claim that a content refresh reuses already-tested code then has to be
enforced rather than assumed: the job checks, with one workflow-runs API call
using the ambient token, that the code it is about to publish passed. Without
that check, a push whose tests failed would be published by the next cron — a
regression from today, where the cron re-runs the tests.

The obvious form of that check is broken. "HEAD's Deploy run concluded
successfully" deadlocks against the snapshot commits above: a snapshot refresh
moves `main`'s HEAD to a bot commit that has no Deploy run at all, so the very
next cron finds no run for HEAD and declines — and keeps declining until
Anthony pushes code. That the bot commit has no run is itself what stops an
infinite loop: pushes made with the ambient `GITHUB_TOKEN` are documented not
to trigger workflows — untested here; see the risk table. The working rule
instead: the most recent **completed** Deploy run on `main` concluded
`success`, **and** nothing outside `content/snapshot/` has changed
between that run's SHA and HEAD. That both tolerates bot commits and still
refuses to publish code whose tests failed. Implementation note, because it
will bite immediately: `actions/checkout` defaults to `fetch-depth: 1`, so the
prior run's SHA is not in the local history — either deepen the checkout or
compare through the API rather than `git diff`.

The alternative is to accept "main is always green" as this repo's working
reality and skip the gate; open question 3, where the honest cost is this
two-part rule rather than a one-line check.

## Recommendation

A1 + opt-in trigger + operator-loud marking + the zero-npm content-only
workflow with the last-tested-code gate. Three code changes, plus a new
`content/snapshot/` directory, the README playbook, and the offline tests
below: `build.mjs` (`--write-snapshot`, and `--use-snapshot` consulted by
`loadSource` and the sponsor-logo fetch), `deploy.yml` (the dispatch input,
the loud-marking step), and `rebuild-content.yml` (self-contained zero-npm job
plus the gate), with the snapshot-write-and-commit step and its job-scoped
`contents: write` appearing in **both** workflows. On landing, the two BACKLOG
items close and the invariant's "currently not met" clause is Anthony's to
remove.

## Acceptance criteria

All automated criteria run without network, per the loopback convention.

1. **Fallback works and is deterministic.** With a config pointing at a
   loopback URL that refuses connections (and one that 500s), a populated
   snapshot, and the fallback flag: the build succeeds and its `content.json`
   is byte-identical to a build that reads the same bytes as local sources.
   Same setup without the flag: the build fails exactly as today. With the
   flag but no snapshot entry for a source — a newly added tab, or a first
   run — the build fails naming that source rather than publishing a hole.
2. **Snapshot writer is faithful and quiet.** Building against loopback-served
   CSVs writes snapshot bytes identical to what was served, plus correct meta;
   an immediate re-run with unchanged sources rewrites nothing, so no commit
   is generated.
3. **Staleness is loud.** The fallback build's output names each
   snapshot-sourced file and its last-changed date (asserted in a test); the
   workflow annotation and job summary are verified by inspection on the first
   real fallback run, since Actions UI behavior is not testable offline.
4. **The content path is npm-free, gated, and refreshes the snapshot.** The
   reworked workflow contains no npm invocation (assertable by a test reading
   the workflow file), shares the `pages` concurrency group, and carries the
   same snapshot-write-and-commit step as `deploy.yml`. The gate publishes
   when the last completed Deploy run on `main` succeeded and only
   `content/snapshot/` changed since; it declines when that run failed, and it
   still publishes when HEAD is a bot snapshot commit.
5. **Existing guarantees hold.** The determinism check (unchanged sources →
   byte-identical `content.json`, unchanged `sw.js` version) passes on both
   live-shaped and fallback paths, and the full existing suite stays green.
6. **The playbook exists.** README documents both emergency procedures as
   commands to run, not concepts to understand.

## Risks & unknowns

| Risk | Confidence it's fine | Cheapest test |
|---|---|---|
| Bot pushes with `GITHUB_TOKEN` don't re-trigger workflows — if wrong, a snapshot commit re-triggers Deploy and only `[skip ci]` stops a loop | medium-high | watch the first real snapshot commit after merge; `[skip ci]` is carried regardless, per repo convention |
| `contents: write` job scoping and cross-workflow Pages concurrency behave as documented | high | first real cron run after merge |
| Snapshot bot-commit races a concurrent push to main | high | make the commit step best-effort; a missed refresh cycle costs nothing |
| The last-tested-code check is fiddly (which run counts as "completed", re-runs, checkout depth, the snapshot-commit exception) | medium | spike both halves — the `gh api` query and the SHA comparison — by hand before wiring them in |
| `actions/setup-node` resolves Node 24 from the runner toolcache rather than nodejs.org | medium-high | inspect one run's setup-node log; if it downloads, decide then whether pinning or offline-ness wins |
| Snapshot date understates freshness (it records the last content *change*, not the last successful check) | accepted | none — it can understate but never overstate |
| Remote sponsor logos, once that tab is live, fail builds in ways the CSV retry logic doesn't cover | medium | fold logo fetches into the same retry + snapshot machinery (in scope above) |
| Fallback flag plumbing tempts future automation that would mask link rot | medium-high | re-read the cron-never-falls-back rule, stated in the workflow comment, at the next automation change |

## Open questions — Anthony's calls

1. **Fallback trigger:** opt-in dispatch only (recommended), or also automatic
   on push-triggered code deploys, with cron always excluded?
2. **Staleness audience:** operator-only (recommended), or an attendee-visible
   marker too, at the cost of a full re-precache each time it flips on or off?
3. **Content-only gate:** require the last-tested-code check — the two-part
   rule above, since the one-line version deadlocks against snapshot commits —
   or accept "main is always green" as the working reality and skip it? The
   complexity is real; so is the cron silently publishing a red build
   without it.
4. **npm-down code deploys:** defer entirely (the invariant doesn't demand
   them), add the cheap npm cache, and/or add an emergency `skip_tests`
   dispatch input despite the gate it weakens?
5. **Repo hygiene:** are bot snapshot commits plus `contents: write` on the
   deploy workflow acceptable here, or does that tip the choice back toward
   A2's commit-free reuse despite its undated, Pages-chained trade-offs?
6. **Snapshot vs fixtures for venues:** `content/fixtures/venues.csv` already
   holds real sheet bytes (CONTRACTS.md calls fixtures placeholder content;
   CLAUDE.md calls this one a committed snapshot of the sheet), so
   `content/snapshot/venues.csv` would duplicate it. Keep both with distinct
   jobs — fixtures for tests, snapshot for emergencies — or reconcile them?

## Ledger

- **Committed snapshot over Pages-reuse (A1 over A2)** — dated staleness,
  validated fallback inputs, no chained remote dependency, offline-testable;
  the costs are bot commits and one permission widening (Q5).
- **A1 generalizes an existing repo pattern** — `tools/make-map.mjs` already
  falls back to a committed `osm-cache.json` behind a `--refresh` flag, so
  this is not a new mechanism to maintain.
- **Opt-in fallback over automatic** (provisional, Q1) — the failed push
  deploy is itself the alarm; automatic fallback would hide a rotted publish
  link behind every code push.
- **No fallback for wrong-but-reachable sources** — sign-in pages, emptied
  tabs, and renamed headers fail hard on every path; that loudness is the
  existing guardrail against link rot and bad edits, and robustness must not
  sand it down.
- **Content refreshes drop the browser suite** — it only ever tested fixture
  content; `build.mjs` validation is and remains the real content gate.
- **Cron writes the snapshot but never reads it** — the 6-hour rebuild is the
  main source of fresh bytes, so it must refresh the fallback; but a refresh
  that cannot fetch fresh content has failed, and must say so rather than
  "succeed" on what it already had.
- **The gate tolerates bot commits by construction** — "HEAD's Deploy run
  passed" deadlocks the moment a snapshot commit lands, so the rule is "last
  completed Deploy run on `main` passed, and only `content/snapshot/` moved
  since".
- **npm-down *code* deploys deferred** (Q4) — outside the invariant's letter;
  `skip_tests` trades away a deliberately built gate; the npm cache only
  helps until the lockfile changes.
- **GitHub outage accepted** — the platform itself; $0 forecloses mitigation.
- **Snapshot ≠ fixtures** — the snapshot is machine-written and feeds only
  emergency builds; fixtures are hand-committed and feed the offline tests.
  Their overlap on venues is Q6.
